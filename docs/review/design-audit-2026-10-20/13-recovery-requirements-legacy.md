**最重要的问题（≤5 条）**

1. `P23-01`（P1）恢复页的身份来自 bootstrap 任务列表（服务只返回最近 100 条），不是 `GET /api/tasks/:id`：当父任务不在最近 100 条内时，页面把可恢复任务显示成“没有可读取的父任务”，恢复入口被错误阻断；`/recovery` 选择列表同样只列这 100 条里需要处理的任务。
2. `P23-02`（P2）设计“不可恢复”是独立空态（当前任务不可恢复 / 没有可复制阶段 / 返回原任务），实现只在“恢复差异预览”里显示一行 `allowed=false` 原因，三张恢复方式卡仍可点选，没有专属结论与返回动作。
3. `P24-03`（P2）“加载更多”只在前 200 条已载入任务内前端切片：`useTasks({limit:200})` + `fetchTasks` 丢弃 `nextCursor/total`，分段计数、项目筛选范围与“已显示 N / 总数”都只覆盖前 200 条；服务其实提供 cursor 分页（`packages/engine/src/project-task.ts:268-282`）。
4. `P25-02`（P2）设计里四个页签与历史子态（overview/perms/prompt/history/history-open/compare）都是 URL 状态（`roles-legacy.html:280-284`），实现是组件内 `useState`：刷新、后退、深链都回到“描述”，无法按设计直达“权限与 MCP / 版本历史 / 所选历史版本 / 版本比较”。
5. `P25-03`（P2）“权限与 MCP”页签只渲染 `resourcePermissions` 原始 JSON：设计要求的权限模式、阶段/项目预览、配置/受限/待核定统计、逐工具 MCP 清单（待运行时核定/策略禁用/角色已禁用）与权限规则表（允许/询问/拒绝·范围）都没有。

## 问题清单

### P23-01: 恢复身份来自 bootstrap 任务列表（最近 100 条），可恢复任务会被误判“无父任务”
- **严重度**：P1
- **维度**：S / R / D
- **类别**：状态 / 数据契约
- **设计依据**：`opencode-workflow-design-showcase/originals/main/pages/recovery.html:96-100`（面包屑/父任务身份与返回原任务）、`:156`（no-parent 仅表示“恢复地址对应的任务不存在或已不可见”）。
- **实现位置**：`REC:130-132`（`task = bootstrap.data.tasks.find(...)` 作为唯一身份来源）、`REC:214-228`（`task===undefined` 即显示“没有可读取的父任务”）；`REC:139-144` 已另有 `GET /api/tasks/:id/detail` 但未用于身份判定；`HTTP:392`（bootstrap 只返回 `engine.tasks.list({ limit: 100 })`）；`REC:197-200,240-269`（`/recovery` 选择态同样只列这 100 条中有 attention 的任务）。
- **差异**：设计以恢复地址携带的父任务身份读取上下文；实现把“父任务是否在最近 100 条任务摘要里”当作“父任务是否存在”。任务总量 >100 或目标任务较旧时，服务明明有该任务与失败执行，页面却显示 no-parent 并完全阻止创建恢复草稿；`/recovery` 的候选列表也会漏掉这些任务。
- **原因**：直接原因：页面用 bootstrap 摘要列表做身份判定，而不是按 `taskId` 读取详情（C6）；根本原因：`REC` 的 detail 查询只用于执行区块，未承担身份解析；bootstrap 只给 100 条摘要（C1）。
- **影响**：>100 任务的真实项目中旧的失败任务无法从恢复页恢复；用户会误以为任务不存在/已不可见。
- **建议**：身份改用 `GET /api/tasks/:id/detail`（或其摘要）结果判定；`/recovery` 选择列表改用 `listPage({attention})` 分页或搜索，而不是 bootstrap 前 100 条；no-parent 仅在 detail 返回 404/无权限时显示。
- **验证**：静态（依赖链可判定）；>100 任务场景需 GUI/真实服务。
- **关联状态**：`no-parent, default`

### P23-02: “不可恢复”没有专属空态与返回动作
- **严重度**：P2
- **维度**：S / 结构 / D
- **类别**：状态 / 结构
- **设计依据**：`originals/main/pages/recovery.html:129`（ineligible 专属空态：“当前任务不可恢复 / 这个任务已完成，没有可复制的失败阶段 / 返回原任务”）、`:104-110`（原任务状态、恢复起点“没有可复制阶段”）、`:115`（查看原任务证据）。
- **实现位置**：`REC:196`（`createBlocked` 含 `!preview.data?.allowed`）、`REC:351-353`（只在“恢复差异预览”里输出 `preview.data.reason` 一行）；`REC:307-347`（三种方式卡仍渲染且可选）、`REC:286-363`（右侧设置卡完整显示）。
- **差异**：设计对“已完成/无失败阶段/服务判定不可恢复”给出整页结论、原因与返回原任务；实现仍是可操作的恢复设置页，仅在预览区用一行 reason 阻止创建，用户不易判断“这个任务根本不能恢复”。
- **原因**：直接原因：只把预览 `allowed=false` 当禁用条件，没有独立状态分支（C2）；根本原因：读模型只有 `allowed/reason`，缺少“不可恢复原因类型/可恢复起点”的结构化结论（C1）——`RecoveryPreview.reason` 为自由文本（`CONTRACTS:1272-1281`）。
- **影响**：用户会反复点选恢复方式、尝试创建后才发现不可恢复；缺少“返回原任务”的明确出口。
- **建议**：`preview.allowed===false` 时切换为不可恢复空态（原因、原任务返回），并隐藏/禁用恢复方式与创建区；服务 reason 建议区分 `ineligible-completed`/`no-failed-stage` 等类型。
- **验证**：静态；真实已完成任务场景需 GUI/真实服务。
- **关联状态**：`ineligible`

### P23-03: 页面多出“执行恢复”区块，与设计的三段结构不符
- **严重度**：P2
- **维度**：结构 / A
- **类别**：结构 / 范围
- **设计依据**：`originals/main/pages/recovery.html:151-158`（恢复页只有“失败上下文 / 怎样恢复 / 派生草稿”三段）、`:125-139`（右侧只有恢复方式与创建）；`sources/supplement-v4/DESIGN-DELTA-v4.md:24`（恢复面板、整体推进等既有能力都在统一任务画布）。
- **实现位置**：`REC:366-503`（新增“执行恢复”卡片：继续执行/按原配置重试/取消执行/跳过节点及下游 + 失败节点列表 + UNKNOWN 提示）。
- **差异**：设计要求恢复页只创建派生草稿，执行恢复动作属于统一任务画布；实现在恢复页复制了一套执行控制（resume/retry/cancel/skip），页面从三段变四段，并出现与任务画布重复的写操作入口。
- **原因**：直接原因：把任务画布的执行恢复能力搬进了恢复页（C4）；根本原因：恢复页设计与统一画布能力划分未在实现中保持一致（C4/C6）。
- **影响**：同一能力两个入口，权限/原请求语义与任务画布分离；破坏设计的信息架构。E34 已对功能做过正式 GUI 验收，但设计权威页没有该区块。
- **建议**：与 Lead/设计 owner 确认归属：把执行恢复动作移回统一任务画布（`/tasks/:id`），恢复页仅保留派生草稿；若确需保留，补设计增量来源，否则按多余区域处理。
- **验证**：静态（区块存在可判定）；移除后的回归需 GUI。
- **关联状态**：`default, unknown`

### P23-04: 失败上下文缺“失败原因分组/尝试次数/查看原任务证据”
- **严重度**：P2
- **维度**：结构 / T / 数据诚实
- **类别**：结构 / 文案
- **设计依据**：`originals/main/pages/recovery.html:111-113`（失败原因两块：验证未通过的 3 条用例断言、“尝试次数已用完 3/3”）、`:114`（阶段列表含恢复起点标记）、`:115`（查看原任务证据）。
